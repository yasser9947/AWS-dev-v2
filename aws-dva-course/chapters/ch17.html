المستخدمون، المجموعات، والأدوار Users, Groups, Roles

IAM اختصار لـ Identity and Access Management، وهي خدمة عالميّة (Global) لا ترتبط بمنطقة. الحساب الجذر (Root) يُنشَأ تلقائياً عند فتح الحساب، لكن لا يجب استخدامه للعمل اليوميّ؛ بل أنشئ مستخدمين IAM فرديين.

IAM is Identity and Access Management — a global service (no region). The root account is created on signup but should not be used day-to-day; create individual IAM users instead.

UserUser

كائن يمثّل شخصاً فيزيائياً. يملك كلمة مرور و/أو Access Keys.

Represents a physical human. Has a password and/or Access Keys.

GroupGroup

حاوية للمستخدمين فقط (لا تحوي مجموعات أخرى). السياسات تُرفَق بالمجموعة وترث للأعضاء.

Container for users only (no nested groups). Policies attach to the group and inherit to members.

RoleRole

هويّة بلا كلمة مرور؛ تُسنَد للخدمات أو للمستخدمين مؤقّتاً عبر AssumeRole.

Identity without a password; assumed by services or users temporarily via AssumeRole.

مفهوم أساسي:Key concept: قاعدة ذهبيّة: مستخدم واحد لكلّ شخص، دور واحد لكلّ خدمة/تطبيق. لا تشارك الـ Access Keys أبداً، ولا تستخدم الـ Root إلّا لإعداد الحساب الأوليّ ثمّ فعّل MFA عليه وضع مفاتيحه جانباً. Golden rule: one user per person, one role per service/app. Never share Access Keys. Use Root only for initial account setup, then enable MFA and store its keys safely.

بنية سياسة JSON وأنواعها JSON policy structure & types

السياسة في AWS عبارة عن مستند JSON بعناصر ثابتة: Version, Statement (واحدة أو أكثر). كلّ Statement فيها: Effect (Allow/Deny)، Action، Resource، وCondition اختياريّة.

An AWS policy is a JSON document with fixed elements: Version, Statement (one or more). Each statement has: Effect (Allow/Deny), Action, Resource, and optional Condition.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowReadMyBucket",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:ListBucket"
      ],
      "Resource": [
        "arn:aws:s3:::acme-reports",
        "arn:aws:s3:::acme-reports/*"
      ],
      "Condition": {
        "IpAddress": { "aws:SourceIp": "203.0.113.0/24" },
        "Bool":      { "aws:MultiFactorAuthPresent": "true" }
      }
    }
  ]
}

Identity-basedIdentity-based

تُرفَق بمستخدم أو مجموعة أو دور. تجيب عن سؤال: ماذا يستطيع هذا المستخدم أن يفعل؟

Attached to a user/group/role. Answers: what can this principal do?

Resource-basedResource-based

تُرفَق بالمورد نفسه (Bucket Policy, KMS Key Policy). تجيب عن سؤال: من يستطيع الوصول إلى هذا المورد؟ وتدعم الوصول عبر الحسابات.

Attached to the resource (Bucket Policy, KMS Key Policy). Answers: who can access this resource? and supports cross-account access.

منطق تقييم السياسات Policy evaluation logic

عند كلّ طلب API، يقيّم IAM جميع السياسات المنطبقة (Identity-based + Resource-based + SCP + Session). الترتيب الحاسم:

On every API call, IAM evaluates all applicable policies (Identity-based + Resource-based + SCP + Session). Decisive order:

١. Explicit Deny يفوز1. Explicit Deny wins

أيّ Deny صريح يرفض الطلب فوراً.

Any explicit Deny rejects the request immediately.

٢. Explicit Allow يسمح2. Explicit Allow permits

في غياب Deny، أيّ Allow صريح يمرّر الطلب.

Absent a Deny, any explicit Allow permits it.

٣. Implicit Deny افتراضيّ3. Implicit Deny default

عدم وجود Allow = Deny. AWS آمنة افتراضياً.

No Allow = Deny. AWS is secure by default.

فخّ شائع:Common pitfall: سؤال امتحان كلاسيكيّ: IAM Policy تسمح للمستخدم بـ s3:GetObject، لكن Bucket Policy فيها Deny صريح عليه. هل يستطيع القراءة؟ الجواب: لا — الـ explicit Deny في أيّ سياسة يفوز دائماً. Classic exam scenario: IAM policy allows s3:GetObject, but Bucket Policy has an explicit Deny on the user. Can they read? Answer: No — an explicit Deny anywhere always wins. 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyIfNotFromCorporateVPN",
      "Effect": "Deny",
      "Action": "*",
      "Resource": "*",
      "Condition": {
        "NotIpAddress": {
          "aws:SourceIp": ["198.51.100.0/24", "203.0.113.0/24"]
        },
        "Bool": { "aws:ViaAWSService": "false" }
      }
    }
  ]
}

MFA وسياسة كلمات المرور MFA & password policy

MFA (كلمة المرور تعرفها + جهاز تملكه) هي أهمّ طبقة حماية ضد سرقة كلمات المرور. AWS يدعم: تطبيقات مثل Google Authenticator و Authy، مفاتيح U2F مثل YubiKey، و Hardware Key Fobs.

MFA (password you know + device you own) is the single most important protection against stolen passwords. AWS supports: apps like Google Authenticator/Authy, U2F keys like YubiKey, and Hardware Key Fobs.

    ],

    "Condition": {
      "BoolIfExists": { "aws:MultiFactorAuthPresent": "false" }
    }
  }]
}

أدوار الخدمات وطرق الوصول Service roles & access methods

هناك ثلاث طرق للوصول إلى AWS: Console (كلمة مرور + MFA)، CLI و SDK (Access Keys). لخدماتك في AWS نفسه (EC2, Lambda, ECS) استخدم IAM Roles دائماً — لا مفاتيح مُبرمجة أبداً.

Three ways to access AWS: Console (password + MFA), CLI and SDK (Access Keys). For AWS services themselves (EC2, Lambda, ECS) always use IAM Roles — never hardcoded keys.

// Java SDK v2 with IAM Role from Instance Profile (no keys in code!)
import software.amazon.awssdk.services.s3.S3Client;
import software.amazon.awssdk.auth.credentials.DefaultCredentialsProvider;

S3Client s3 = S3Client.builder()
    .credentialsProvider(DefaultCredentialsProvider.create())
    .build();

// DefaultCredentialsProvider checks (in order):
//  1. Environment variables
//  2. Java System properties
//  3. Credentials file (~/.aws/credentials)
//  4. ECS container credentials
//  5. EC2 Instance Profile metadata (IMDSv2)
// If running on EC2 with a role attached, keys are fetched automatically & rotated.
للمطوّر السينيور:For the senior dev: للمطوّر السينيور: لا تعتمد على IMDSv1 بعد الآن. افرض IMDSv2 (Session-based) عند إطلاق الخادم؛ فهو يتطلّب رمز PUT قبل قراءة البيانات الوصفيّة ويمنع هجمات SSRF المعروفة (مثل Capital One 2019). Senior tip: don't rely on IMDSv1 anymore. Enforce IMDSv2 (session-based) at launch; it requires a PUT token before metadata reads and blocks SSRF-based credential theft (e.g., Capital One 2019).

أدوات التدقيق: Credentials Report و Access Analyzer Audit tools: Credentials Report & Access Analyzer

AWS تقدّم ثلاث أدوات مجانيّة للتدقيق:

AWS provides three free audit tools:

Credentials ReportCredentials Report

تقرير على مستوى الحساب يعرض جميع المستخدمين وحالة كلمات مرورهم ومفاتيحهم و MFA.

Account-level CSV listing every user's password, keys, and MFA status.

Access AdvisorAccess Advisor

على مستوى المستخدم: يعرض آخر مرّة استُخدمت فيها كلّ خدمة ضمن صلاحيّاته.

User-level: shows when each service was last used by that principal.

Access AnalyzerAccess Analyzer

يكتشف الموارد المُشارَكة مع هويّات خارجيّة (حسابات أخرى أو عموم الإنترنت).

Detects resources shared with external identities (other accounts or public).

# Generate IAM Credentials Report (CSV)
aws iam generate-credential-report
aws iam get-credential-report --query Content --output text | base64 -d > creds.csv

# Use Access Analyzer via the Policy Simulator
aws iam simulate-principal-policy \
  --policy-source-arn arn:aws:iam::111122223333:role/BackendRole \
  --action-names s3:GetObject s3:PutObject \
  --resource-arns arn:aws:s3:::acme-prod/*
مفهوم أساسي:Key concept: Policy Simulator أداة لا تُقدَّر بثمن: تختبر أثر السياسات قبل تطبيقها. استخدمها في كلّ Pull Request يعدّل صلاحيّات الإنتاج. Policy Simulator is invaluable — tests a policy's effect before you deploy it. Run it on every PR that modifies production permissions.

    Console access only, add to the group, require password change on first sign-in.

DAI لمنطق التقييم: Deny (explicit) → Allow (explicit) → Implicit deny. تذكّر: الرافض يحسم، المُجيز يُجيز، والصمت رفض.
