ما هي AWS STS ولماذا نحتاجها What is AWS STS and why we need it

AWS STS (Security Token Service) خدمة عالميّة تُصدر credentials مؤقّتة (١٥ دقيقة حتى ١٢ ساعة). بدلاً من مفاتيح IAM دائمة تخزّنها على خادم، يطلب التطبيق من STS رمزاً مؤقّتاً يُلغى تلقائياً — وهذا أساس النموذج الأمنيّ الحديث في AWS.

AWS STS (Security Token Service) is a global service that issues temporary credentials (15 min to 12h). Instead of permanent IAM keys stored on a server, your app asks STS for a short-lived token that auto-expires — this is the foundation of AWS's modern security model.

Every STS output returns 4 fields: AccessKeyId, SecretAccessKey, SessionToken, and Expiration. SessionToken is mandatory on every API call with temp credentials.

Trust Policy vs Permissions Policy Trust Policy vs Permissions Policy

كلّ IAM Role له سياستان متكاملتان:

Every IAM Role has two complementary policies:

Trust Policy (AssumeRolePolicyDocument)Trust Policy (AssumeRolePolicyDocument)

تجيب: من يستطيع أن يتحمّل هذا الدور؟ تُحدَّد فيها Principal (حساب، خدمة، IdP). بدونها لا أحد يستطيع الوصول.

Answers: who may assume this role? Specifies Principal (account, service, IdP). Without it, nobody can.

Permissions PolicyPermissions Policy

تجيب: ماذا يستطيع من يتحمّل الدور أن يفعل؟ نفس صيغة IAM policy العاديّة (Allow/Deny على Action/Resource).

Answers: what can the assumer do? Same format as an IAM policy (Allow/Deny on Action/Resource).

// Trust Policy: account 222222222222 can assume this role
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "AWS": "arn:aws:iam::222222222222:root"
    },
    "Action": "sts:AssumeRole",
    "Condition": {
      "StringEquals": {
        "sts:ExternalId": "Acme-External-9fK2pL"
      },
      "Bool": {
        "aws:MultiFactorAuthPresent": "true"
      }
    }
  }]
}
فخّ شائع:Common pitfall: خلط شائع: Trust Policy ليست "Permissions" — لا تضف فيها s3:GetObject. الـ Trust فقط تحدّد من يدخل، والـ Permissions تحدّد ماذا يفعل بعد الدخول. Common mix-up: Trust Policy is not Permissions — don't add s3:GetObject here. Trust decides who enters; Permissions decides what they do once in.

تدفّق Cross-Account AssumeRole Cross-Account AssumeRole flow

السيناريو: مستخدم في الحساب A (Dev) يحتاج الوصول لمورد في الحساب B (Prod). الحلّ المعياريّ:

Scenario: a user in Account A (Dev) needs to access a resource in Account B (Prod). Standard solution:

١. Account B يُعرّف دور1. Account B defines a role

Trust Policy تسمح لـ Account A فقط. Permissions تحدّد ما يستطيع فعله.

Trust Policy allows Account A only. Permissions define what it can do.

٢. Account A يمنح المستخدم2. Account A grants the user

سياسة IAM تسمح للمستخدم بعمل sts:AssumeRole على ARN الدور في B.

IAM policy allowing sts:AssumeRole on the role ARN in B.

٣. المستخدم ينادي STS3. User calls STS

aws sts assume-role --role-arn ... يحصل على مفاتيح مؤقّتة.

aws sts assume-role --role-arn ... returns temp credentials.

٤. يستخدمها في B4. Uses them in B

الطلبات تحمل SessionToken وتُقيَّد بمدة الجلسة.

Requests carry the SessionToken, bounded by session duration.

# Account A: user 'alice' calls STS
aws sts assume-role \
  --role-arn arn:aws:iam::222222222222:role/CrossAccountProdRead \
  --role-session-name alice-prod-access \
  --external-id Acme-External-9fK2pL \
  --duration-seconds 3600

# Returns JSON with temp AccessKeyId/SecretAccessKey/SessionToken
# Export as env vars and call AWS in Account B
export AWS_ACCESS_KEY_ID=ASIA...
export AWS_SECRET_ACCESS_KEY=...
export AWS_SESSION_TOKEN=...
aws s3 ls s3://prod-reports/
للمطوّر السينيور:For the senior dev: السبب الجوهريّ لاستخدام Roles لا Users عبر الحسابات: لا تُنقَل مفاتيح طويلة الأجل بين الحسابات، التدقيق موحَّد عبر CloudTrail (AssumeRole يظهر في كلا الحسابين)، والمفاتيح تنتهي تلقائياً. Cross-account User-based = كابوس تدقيق ومفاتيح ضائعة. Why Roles, not Users for cross-account: no long-term keys travel between accounts, unified audit via CloudTrail (AssumeRole appears in both accounts), and keys expire on their own. Cross-account User-based = audit nightmare and lost keys.

External ID ومشكلة Confused Deputy External ID & the Confused Deputy problem

Confused Deputy هجمة كلاسيكيّة: عميل (SaaS) يتحمّل دوراً في حساب عميله. لو علم مهاجم بـ ARN الدور وانتحل شخصيّة عميل آخر، سيصل إلى موارده. الحلّ: External ID — سرّ مشترك بين SaaS وعميله يجب تقديمه في كلّ AssumeRole.

Confused Deputy is a classic attack: a SaaS provider assumes a role in a customer account. If an attacker learns the role ARN and pretends to be a different customer, they'd reach its resources. Fix: External ID — a shared secret between SaaS and customer, required on every AssumeRole.

// Customer's Trust Policy — External ID required
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "AWS": "arn:aws:iam::999999999999:root"  // SaaS account
    },
    "Action": "sts:AssumeRole",
    "Condition": {
      "StringEquals": {
        "sts:ExternalId": "unique-per-customer-secret-42"
      }
    }
  }]
}
نصيحة للامتحان:Exam tip: External ID ليس كلمة سرّ قويّة — لا تثق بها وحدها. هدفها منع الخلط عند تعدّد العملاء، لا استبدال MFA أو التشفير. يُولَّد بواسطة مزوّد SaaS ويُحفَظ في سجلّه. External ID isn't a strong secret — don't rely on it alone. Its purpose is to prevent mix-ups across customers, not replace MFA/encryption. It's generated by the SaaS provider and kept in their DB.

PassRole والتفويض للخدمات PassRole & delegating to services

عند إعداد خدمة مثل EC2 أو Lambda أو CodePipeline، تمرّر لها IAM Role لتستخدمه. ذلك يتطلّب صلاحيّة خاصّة اسمها iam:PassRole على المستخدم الذي يعدّ الخدمة. بدونها، يفشل الإعداد حتى لو كانت كلّ الصلاحيّات الأخرى موجودة.

When configuring a service like EC2, Lambda, or CodePipeline, you pass it an IAM Role. This requires a special permission: iam:PassRole on the user setting up the service. Without it, setup fails even if all other permissions exist.

// Developer's policy to let them launch EC2 with role
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["ec2:RunInstances"],
      "Resource": "*"
    },
    {
      "Effect": "Allow",
      "Action": ["iam:PassRole", "iam:GetRole"],
      "Resource": "arn:aws:iam::111122223333:role/EC2AppRole",
      "Condition": {
        "StringEquals": {
          "iam:PassedToService": "ec2.amazonaws.com"
        }
      }
    }
  ]
}
فخّ شائع:Common pitfall: لا تفتح iam:PassRole على Resource: *. مطوّر يمكنه تمرير دور AdminRole إلى Lambda ضارّة ويرتقي صلاحيّاته — ثغرة Escalation كلاسيكيّة. قيّد PassRole إلى ARN محدّد مع iam:PassedToService. Never open iam:PassRole to Resource: *. A dev could pass AdminRole to a malicious Lambda and escalate — classic escalation vuln. Restrict PassRole to specific ARNs with iam:PassedToService.

السياسات الديناميكيّة: متغيّرات وشروط Dynamic policies: variables & conditions

Policy Variables تجعل سياسة واحدة تخدم عدّة مستخدمين. الأهمّ: ${aws:username}، ${aws:userid}، ${aws:SourceIp}. Conditions تضيف منطق: IP، وقت، MFA، Tags، VPC.

Policy Variables let one policy serve many users. Key: ${aws:username}, ${aws:userid}, ${aws:SourceIp}. Conditions add logic: IP, time, MFA, tags, VPC.

// One policy giving every user their own S3 'home' folder
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowListingOfUserFolder",
      "Effect": "Allow",
      "Action": ["s3:ListBucket"],
      "Resource": ["arn:aws:s3:::acme-home"],
      "Condition": {
        "StringLike": {
          "s3:prefix": ["home/${aws:username}/*"]
        }
      }
    },
    {
      "Sid": "AllowAllS3ActionsInUserFolder",
      "Effect": "Allow",
      "Action": ["s3:*"],
      "Resource": ["arn:aws:s3:::acme-home/home/${aws:username}/*"]
    }
  ]
}

aws:SourceIpتقييد الـ API حسب IP المصدر.Restrict API by source IP.
aws:MultiFactorAuthPresentفرض MFA على عمليّات معيّنة.Require MFA for sensitive ops.
aws:RequestedRegionحصر المنطقة (Region).Limit to a region.
aws:PrincipalTag/Deptربط الصلاحيّة بـ Tag على الهويّة (ABAC).Tie permission to a principal tag (ABAC).
