قواعد البيانات المُدارة: RDS و Aurora و ElastiCache Managed Databases: RDS, Aurora & ElastiCache

لماذا تترك AWS تدير قواعد بياناتك بدل تشغيلها بنفسك على EC2؟ النسخ الاحتياطيّ التلقائيّ، التصحيح (patching)، الـ Failover، والـ Read Replicas — كلّها دون SSH. هذه الفصل يغطّي الفرق العمليّ بين RDS و Aurora و ElastiCache، ومتى تختار كلّ واحدة. Why let AWS manage your DB instead of running it yourself on EC2? Automated backups, patching, failover, and read replicas — all without SSH. This chapter covers the practical differences between RDS, Aurora, and ElastiCache, and when to pick each.

RDS — قاعدة بيانات مُدارة RDS — Managed Relational Database Service

RDS (Relational Database Service) يشغّل قاعدة بيانات علائقيّة بالنيابة عنك. يدعم سبعة محرّكات: PostgreSQL، MySQL، MariaDB، Oracle، Microsoft SQL Server، IBM DB2، و Aurora (بنكهتَي PostgreSQL و MySQL). بالمقابل: لا تستطيع الدخول عبر SSH (باستثناء RDS Custom).

RDS (Relational Database Service) runs a relational DB on your behalf. Supports seven engines: PostgreSQL, MySQL, MariaDB, Oracle, Microsoft SQL Server, IBM DB2, and Aurora (PostgreSQL and MySQL flavors). In exchange: no SSH access (except RDS Custom).

توفير وتصحيح تلقائيAutomated provisioning & patching

لا حاجة لتثبيت أو تحديث نظام تشغيل.

No OS install or patching required.

استعادة إلى أيّ ثانية خلال فترة الاحتفاظ (حتى ٣٥ يوم).

Restore to any second within retention (up to 35 days).

Monitoring مدمجBuilt-in monitoring

CloudWatch dashboards و Enhanced Monitoring و Performance Insights.

CloudWatch dashboards, Enhanced Monitoring, Performance Insights.

Failover تلقائيّ وتوسعة القراءة.

Automatic failover and read scaling.

فخّ شائع:Common pitfall: RDS لا يسمح بـ SSH. إن احتجت لتثبيت مكتبة أو سكربت نظام (مثلاً Oracle Data Guard المخصّص)، استخدم RDS Custom الذي يعطيك وصولاً لـ OS. عدا ذلك، استخدم EC2 وتدير قاعدة البيانات بنفسك — مع فقدان كلّ مزايا الإدارة. RDS doesn't allow SSH. If you need to install a library or system script (e.g., Oracle Data Guard customizations), use RDS Custom which grants OS access. Otherwise, run on EC2 yourself — losing all managed-service benefits.

RDS Storage Auto Scaling: يزيد مساحة التخزين تلقائياً عندما تنخفض المساحة الحرّة لـ ١٠٪ ويستمرّ الانخفاض ٥ دقائق و مرّت ٦ ساعات على آخر تعديل. تحدّد أنت الحدّ الأقصى (Maximum Storage Threshold). يُعفيك من مراقبة مساحة التخزين يدوياً.

RDS Storage Auto Scaling: grows storage when free space drops below 10%, stays low 5+ minutes, and 6+ hours since last change. You set the Maximum Storage Threshold. Frees you from manual storage monitoring.

Read Replicas vs Multi-AZ — فرق كبير Read Replicas vs Multi-AZ — a critical distinction

هذا أكثر موضوع يخلطه المرشّحون. Read Replicas للتوسعة (scale reads)، و Multi-AZ للإتاحة العالية (HA / DR). لا بديل بينهما — بل كثيراً ما يُستخدمان معاً.

The most commonly confused topic. Read Replicas scale reads, Multi-AZ provides HA / DR. They're not alternatives — often used together.

Read Replicas — للقراءةRead Replicas — for reads

حتى ١٥ نسخة قراءة (RDS) أو ١٥ Aurora Replica في Aurora. تكرار غير متزامن (ASYNC) — القراءة قد تكون قديمة لحظياً (eventually consistent). يمكن وضعها في نفس AZ، AZ مختلفة، أو Region مختلفة. التطبيق يجب أن يعرف كيف يوجّه reads إلى الـ replica (connection string مختلف).

Up to 15 read replicas (RDS) or 15 Aurora Replicas. Asynchronous replication — reads may be momentarily stale (eventually consistent). Can live in same AZ, different AZ, or different Region. The app must know to route reads to the replica (different connection string).

Multi-AZ — للإتاحة العاليةMulti-AZ — for HA

نسخة احتياطيّة واحدة (standby) في AZ مختلفة بتكرار متزامن (SYNC). DNS endpoint واحد — عند فشل الـ master، يقع الـ failover تلقائياً إلى الـ standby (دقائق قليلة). لا تستخدم للقراءة — الـ standby غير متاح للاستعلامات. الغرض الوحيد: صمود كارثة AZ.

One standby in a different AZ, synchronous replication. Single DNS endpoint — on master failure, auto-failover to standby (few minutes). Not used for reads — standby isn't queryable. Sole purpose: survive an AZ outage.

نصيحة للامتحان:Exam tip: خدعة شائعة في الامتحان: السؤال يقول "تطبيق reporting بطيء بسبب استعلامات على قاعدة الإنتاج". الجواب: Read Replica لا Multi-AZ. Multi-AZ يحلّ HA فقط. Common exam trap: "reporting app slow due to queries on prod DB". Answer: Read Replica, not Multi-AZ. Multi-AZ solves HA only. 
// Spring Boot — using separate data sources for read/write
// With RDS: write URL = master, read URL = replica
@Configuration
public class DbConfig {
    @Bean
    @ConfigurationProperties("spring.datasource.write")
    public DataSource writeDataSource() {
        // jdbc:postgresql://acme-master.xyz.us-east-1.rds.amazonaws.com:5432/acme
        return DataSourceBuilder.create().build();
    }

    @Bean
    @ConfigurationProperties("spring.datasource.read")
    public DataSource readDataSource() {
        // jdbc:postgresql://acme-read-replica.xyz.us-east-1.rds.amazonaws.com:5432/acme
        return DataSourceBuilder.create().build();
    }

    // AbstractRoutingDataSource picks the right one based on @Transactional(readOnly=true)
}

// With Aurora: single reader endpoint load-balances across all replicas automatically
للمطوّر السينيور:For the senior dev: للمطوّر السينيور: Read Replica غير متزامنة، لذا قراءة بعد كتابة قد تعيد قيمة قديمة. لا تضع عملية read-after-write على الـ replica إلّا إن كنت تقبل eventually consistent. في Aurora، replica lag أقلّ من ١٠ ميلّي ثانية عادة — أفضل بكثير من RDS. Senior note: Read Replicas are async, so a read-after-write may see stale data. Don't route read-after-write to a replica unless you accept eventual consistency. In Aurora, replica lag is typically sub-10ms — much better than RDS.

Aurora — قاعدة بيانات AWS الخاصّة Aurora — AWS's proprietary database

Aurora محرّك قواعد بيانات ملكيّ من AWS، متوافق wire-protocol مع PostgreSQL و MySQL (driverكَ يعمل بدون تعديل). يدّعي AWS ٥× سرعة MySQL و ٣× سرعة PostgreSQL، لأنّه مُعاد تصميمه بالكامل ليستفيد من بنية AWS.

Aurora is AWS's proprietary DB engine, wire-compatible with PostgreSQL and MySQL (your existing drivers work). AWS claims 5× MySQL, 3× PostgreSQL performance — it's entirely re-architected to leverage AWS infrastructure.

تخزين موزّع تلقائياًAuto-distributed storage

٦ نسخ عبر ٣ AZs، تنمو تلقائياً من ١٠ GB إلى ١٢٨ TB.

6 copies across 3 AZs, auto-grows from 10 GB to 128 TB.

Failover فوريّInstant failover

أقلّ من ٣٠ ثانية — HA محليّ.

Under 30 seconds — native HA.

حتى ١٥ Aurora ReplicaUp to 15 Aurora Replicas

replica lag أقلّ من ١٠ ميلّي ثانية.

Replica lag under 10ms.

Cross-Region ReplicationCross-Region replication

لأغراض DR العالميّة.

For global DR.

Aurora Endpoints: Writer Endpoint يشير للـ master (كتابة). Reader Endpoint يوزّع الاتّصالات تلقائياً على replicas (قراءة). بذلك لا تحتاج logic توجيه معقّد في التطبيق كما في RDS.

Aurora Endpoints: Writer Endpoint points to master (writes). Reader Endpoint load-balances connections across replicas (reads). No need for complex routing logic in the app like with RDS.

متى تختار RDS؟When to pick RDS?

عندك حِمل متوسّط، تستخدم محرّكاً لا يدعمه Aurora (Oracle, SQL Server, DB2, MariaDB)، أو تريد أقلّ تكلفة. RDS أرخص بـ ٢٠٪ من Aurora في معظم السيناريوهات.

Moderate load, using an engine Aurora doesn't support (Oracle, SQL Server, DB2, MariaDB), or want minimum cost. RDS is ~20% cheaper than Aurora in most cases.

متى تختار Aurora؟When to pick Aurora?

عند الحاجة لأداء عالٍ، توسعة تلقائيّة serverless (Aurora Serverless v2)، DR عالميّ (Aurora Global Database)، أو صيانة بدون انقطاع. اختره عندما تستخدم MySQL أو PostgreSQL ويهمّك الأداء.

For high throughput, serverless auto-scaling (Aurora Serverless v2), global DR (Aurora Global Database), or zero-downtime maintenance. Choose when MySQL or PostgreSQL and performance matters.

نصيحة:Tip: Aurora Backtrack: ميزة فريدة تعيد قاعدة البيانات إلى حالة سابقة في الزمن (حتى ٧٢ ساعة) بدون استعادة من backup — عمليّة دقائق بدلاً من ساعات. مفيدة جداً للتعافي من قرارات خاطئة (DELETE بدون WHERE). Aurora Backtrack: unique feature that rewinds the DB to a past state (up to 72 hours) without restoring from backup — minutes instead of hours. Great for recovering from human error (DELETE without WHERE).

أمن RDS/Aurora و RDS Proxy RDS/Aurora security and RDS Proxy

التشفير في الراحة (at-rest): عبر AWS KMS. يجب تفعيله عند إنشاء القاعدة — لتشفير قاعدة غير مشفَّرة، خذ Snapshot ثمّ أعد الاستعادة كمشفَّرة. التكرار (replicas) يرث نفس إعدادات التشفير من master.

At-rest encryption: via AWS KMS. Must be enabled at creation — to encrypt an unencrypted DB, snapshot and restore as encrypted. Replicas inherit the master's encryption setting.

RDS Proxy: proxy مُدار يجلس بين تطبيقك وRDS. يجمع الاتّصالات (connection pooling) ويشاركها بين العملاء، ممّا يقلّل الضغط على قاعدة البيانات. يُخفّض زمن failover بنسبة ٦٦٪. مهمّ جداً لتطبيقات Lambda (كلّ invocation ينشئ اتّصالاً جديداً — Proxy يحلّ هذه المشكلة). غير متاح للوصول العامّ — يُستخدم من داخل VPC فقط.

RDS Proxy: a managed proxy between your app and RDS. Pools connections and shares them across clients, reducing DB pressure. Cuts failover time by 66%. Critical for Lambda (each invocation opens a connection — Proxy solves this). Never publicly accessible — VPC-only.

ElastiCache — Redis و Memcached مُدارَين ElastiCache — managed Redis and Memcached

ElastiCache ل Redis أو Memcached كما RDS لقواعد البيانات العلائقيّة. يخفّض الحِمل على RDS بتخزين نتائج الاستعلامات المتكرّرة في الذاكرة، ويجعل تطبيقك stateless بتخزين بيانات الجلسة خارج الخادم.

ElastiCache is to Redis/Memcached what RDS is to relational DBs. Reduces RDS load by caching frequent query results in memory, and makes your app stateless by storing session data externally.

RedisRedis

Multi-AZ مع Auto-Failover. Read Replicas لقراءة موسَّعة و HA. ديمومة (AOF persistence) — البيانات تبقى حتى بعد إعادة التشغيل. Backup و Restore مدمجَين. يدعم هياكل بيانات غنيّة: Sets, Sorted Sets, Hashes, Lists.

Multi-AZ with auto-failover. Read Replicas for scaled reads + HA. Durability via AOF persistence — data survives restart. Built-in backup/restore. Rich data structures: Sets, Sorted Sets, Hashes, Lists.

MemcachedMemcached

Multi-node sharding للتقسيم الأفقي. لا HA (بدون replication). لا ديمومة — البيانات تُفقَد عند إعادة التشغيل. Backup/Restore في الوضع Serverless. معمار multi-threaded. بسيط: key-value فقط.

Multi-node sharding for horizontal partitioning. No HA (no replication). No persistence — data lost on restart. Backup/Restore in Serverless mode. Multi-threaded. Simple: key-value only.

مفهوم أساسي:Key concept: الاختيار البسيط: Redis دائماً إلّا في حالات محدّدة جداً (حاجة لـ sharding خالص بدون HA، أو كود قديم مرتبط بـ Memcached). Redis أكثر مرونة و HA-capable و يدعم ديمومة. Simple rule: Redis always unless very specific cases (pure sharding without HA, or legacy code bound to Memcached). Redis is more flexible, HA-capable, and supports persistence.

أنماط caching شائعة: Lazy Loading (Cache-Aside): يقرأ التطبيق من الـ cache أوّلاً، إذا miss يقرأ من DB ويخزّن النتيجة. Write-Through: كلّ كتابة في DB تُحدّث الـ cache أيضاً. عادة تُستخدم الاستراتيجيّتان معاً.

Common caching patterns: Lazy Loading (Cache-Aside): app reads cache first, on miss reads DB and populates cache. Write-Through: every DB write also updates cache. Usually combined.

// Spring Boot — Redis cache-aside with @Cacheable
@Service
public class UserService {

    @Autowired private UserRepository repo;

    // Lazy loading: cache miss → DB query → populate cache
    @Cacheable(value = "users", key = "#id")
    public User findById(Long id) {
        return repo.findById(id).orElseThrow();
    }

    // Write-through: every save updates cache
    @CachePut(value = "users", key = "#user.id")
    public User save(User user) {
        return repo.save(user);
    }

    // Evict on delete
    @CacheEvict(value = "users", key = "#id")
    public void delete(Long id) {
        repo.deleteById(id);
    }
}

نصيحة:Tip: Amazon MemoryDB for Redis: بديل ElastiCache Redis يقدّم Redis قاعدة بيانات كاملة (durable + Multi-AZ transactional log)، ويصل لأكثر من ١٦٠ مليون طلب/ثانية. يفيد تطبيقات تحتاج سرعة Redis مع ضمان ديمومة DB. Amazon MemoryDB for Redis: alternative to ElastiCache Redis, gives Redis as a full database (durable + Multi-AZ transactional log), 160M+ RPS. Useful when you need Redis speed with DB-grade durability.
