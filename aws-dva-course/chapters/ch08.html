ما هو AWS CLI والـ SDK ومتى تستخدم كلاً منهما AWS CLI vs SDK — when to use which

AWS CLI أداة سطر أوامر مبنية على Python (boto3) للاستخدام اليدوي والسكربتات. الـ SDK مكتبة تستورِدها في كود تطبيقك لتنفيذ العمليات على AWS. كلاهما يستخدم نفس REST APIs ويتّبع نفس سلسلة البحث عن الصلاحيات.

The AWS CLI is a Python-based command-line tool (built on boto3) for manual use and scripts. The SDK is a library you import into your app to call AWS. Both hit the same REST APIs and follow the same credentials chain.

متى CLIWhen CLI

سكربتات النشر، المهام اليدوية، التحقّق السريع، استكشاف الخدمات. سريع ولا يتطلّب بناء مشروع.

Deployment scripts, manual tasks, quick checks, service exploration. Fast, no project build needed.

متى SDKWhen SDK

داخل الخدمات الإنتاجيّة (Spring Boot، Lambda)، عند الحاجة لتدفّق مراقب (streams) أو لتحويل نتائج إلى كائنات Java قويّة الأنواع.

Production services (Spring Boot, Lambda), when you need streaming or strongly-typed Java objects.

لغات SDK الرسميّةOfficial SDK languages

Java، ‎.NET، Node.js، Python (boto3)، Go، Ruby، PHP، C++.

Java, .NET, Node.js, Python (boto3), Go, Ruby, PHP, C++.

حقيقة مفيدةFun fact

الـ CLI نفسها مبنيّة على boto3 — هذا يفسّر تطابق السلوك بين CLI و Python SDK.

The CLI itself is built on boto3 — which is why CLI and Python SDK behave identically.

للمطوّر السينيور:For the senior dev: داخل Spring Boot، استخدم aws-sdk-java-v2 (الإصدار الثاني) لا v1. v2 مبنيّ على Netty، يدعم الاستدعاءات غير المتزامنة عبر CompletableFuture، ويستهلك ذاكرة أقلّ بكثير — مهمّ عند تشغيله داخل Lambda بسبب الـ cold start. Inside Spring Boot, use aws-sdk-java-v2 (v2), not v1. v2 is Netty-based, supports async calls via CompletableFuture, and uses much less memory — critical inside Lambda because of cold starts.

سلسلة البحث عن الصلاحيات في Java SDK v2 Java SDK v2 Default Credentials Provider Chain

عند استدعاء AWS API من Java، الـ SDK يبحث عن الصلاحيات بترتيب محدّد ويتوقف عند أوّل مصدر يعطيه مفاتيح صالحة. فهم هذا الترتيب ضروريّ جداً للامتحان لأنّ AWS تختبره في سيناريوهات محدّدة (مثل: خادم EC2 مع IAM Role لكن متغيّرات البيئة مضبوطة — أيّ يفوز؟).

When you call AWS API from Java, the SDK searches for credentials in a specific order and stops at the first source with valid keys. Exam-critical: AWS tests this with scenarios like "EC2 with IAM Role but env vars set — which wins?".

2متغيّرات البيئةEnvironment VariablesAWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY
3ملفّ الصلاحياتProfile credentials file~/.aws/credentials (shared with CLI)
4صلاحيات حاوية ECSECS container credentialsلمهام ECS (Task Role)For ECS tasks (Task Role)
5صلاحيات Instance ProfileInstance Profile credentialsلخوادم EC2 (IMDS)For EC2 (via IMDS)
فخّ شائع:Common pitfall: سيناريو شائع في الامتحان: مطوّر رفع تطبيقه على EC2، أرفق IAM Role يعطي صلاحية S3 على bucket واحد فقط، لكن التطبيق ما زال يصل إلى جميع الـ buckets. السبب: مفاتيح قديمة في متغيّرات البيئة — الأولوية الأعلى تفوز. الحلّ: حذف متغيّرات البيئة. Common exam scenario: developer deploys to EC2, attaches an IAM Role with S3 access to a single bucket, but the app still accesses all buckets. Reason: old keys in env vars — higher priority wins. Fix: remove env vars. 
// Java SDK v2 — DefaultCredentialsProvider walks the chain automatically
import software.amazon.awssdk.auth.credentials.DefaultCredentialsProvider;
import software.amazon.awssdk.regions.Region;
import software.amazon.awssdk.services.s3.S3Client;

S3Client s3 = S3Client.builder()
    .region(Region.EU_WEST_1)
    .credentialsProvider(DefaultCredentialsProvider.create()) // this is the default too
    .build();

// On EC2 with an attached role, this picks up credentials from IMDS
// In your laptop, it reads ~/.aws/credentials
// Inside Lambda, it uses the Lambda execution role
s3.listBuckets().buckets().forEach(b -> System.out.println(b.name()));

IAM Roles و Instance Profiles و IMDSv2 IAM Roles, Instance Profiles & IMDSv2

Instance Profile هو الحاوية التي تحمل IAM Role وتربطه بخادم EC2. الخادم يقرأ الصلاحيات من Instance Metadata Service (IMDS) على عنوان الشبكة الداخليّ 169.254.169.254. الصلاحيات مؤقّتة (تُجدَّد تلقائياً كل ساعة). هذا هو السبب الذي يجعل استخدام IAM Role أفضل من وضع مفاتيح ثابتة.

An Instance Profile is the container that holds an IAM Role and attaches it to an EC2 instance. The instance reads credentials from the Instance Metadata Service (IMDS) at 169.254.169.254. Credentials are temporary (auto-rotated every hour). That's why IAM Roles beat hardcoded keys.

IMDSv1 (الإصدار القديم)IMDSv1 (legacy)

GET مباشر على الـ URL. معرَّض لهجمات SSRF (Server-Side Request Forgery) التي تخدع التطبيق لقراءة الصلاحيات ثم تسرّبها.

Direct GET on the URL. Vulnerable to SSRF (Server-Side Request Forgery) attacks tricking the app into leaking credentials.

IMDSv2 (الموصى به)IMDSv2 (recommended)

خطوتان: PUT للحصول على Session Token (صلاحيته حتى 6 ساعات)، ثم GET مع الـ token في header. يحظر SSRF لأنّ الثغرات عادة تدعم GET لا PUT.

Two steps: PUT for a session token (up to 6h validity), then GET with the token in a header. Blocks SSRF because typical vulnerabilities only support GET.

# IMDSv2: get a session token, then use it to read metadata
TOKEN=$(curl -X PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")

# Query the attached role name
curl -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/iam/security-credentials/

# Fetch temporary credentials (SDK does this for you)
curl -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/iam/security-credentials/MyRole
مفهوم أساسي:Key concept: أهمّ تمييز: IMDS يعطيك اسم الـ Role والمفاتيح المؤقّتة، لكن لا يعطيك سياسات الـ IAM نفسها. السياسات تُقيَّم داخل AWS عند كلّ استدعاء API. Key distinction: IMDS gives you the role name and temporary credentials, but NOT the IAM policies themselves. Policies are evaluated inside AWS on every API call.

التوقيع بـ Signature v4 (SigV4) Signing requests with Signature v4 (SigV4)

كلّ استدعاء لـ AWS API يجب أن يكون موقّعاً رقميّاً بـ SigV4 ليثبت لـ AWS أنّك تمتلك الـ Secret Access Key. عند استخدام CLI أو SDK يتمّ التوقيع تلقائياً، لكن عند بناء طلبات يدويّة (مثل وضع توقيع على URL لـ S3) تحتاج فهم الآليّة.

Every AWS API call must be signed with SigV4 to prove you hold the Secret Access Key. CLI/SDK sign for you, but when building manual requests (like S3 pre-signed URLs) you need to understand it.

1. Canonical request1. Canonical requestصياغة الطلب بصيغة موحّدة (method, URI, headers, query).Normalize the request (method, URI, headers, query).
2. String to sign2. String to signالتاريخ + الخوارزمية + hash من الـ canonical request.Date + algorithm + hash of canonical request.
3. Signature3. SignatureHMAC-SHA256 باستخدام مفتاح مشتق من Secret Access Key.HMAC-SHA256 using a key derived from the Secret Access Key.
4. Add to request4. Add to requestفي Authorization header أو كـ query string (pre-signed URLs).In Authorization header or as query string (pre-signed URLs).
نصيحة:Tip: S3 pre-signed URLs تستخدم SigV4 في الـ query string مع X-Amz-Signature و X-Amz-Expires. هذا ما يسمح بمشاركة رابط مؤقّت لملفّ خاصّ دون تعريض مفاتيحك. S3 pre-signed URLs use SigV4 in the query string with X-Amz-Signature and X-Amz-Expires. That's how you share a temporary link to a private file without exposing your keys.

Retries و Exponential Backoff Retries & Exponential Backoff

AWS APIs لها حدود معدّلات (rate limits): مثلاً DescribeInstances للـ EC2 بحد 100 استدعاء/ثانية، GetObject على S3 بحد 5500 طلب/ثانية لكلّ prefix. عند تجاوزها يُرجِع AWS خطأ ThrottlingException. الحلّ: Exponential Backoff — انتظار متزايد بين المحاولات.

AWS APIs have rate limits: e.g., EC2 DescribeInstances = 100 calls/sec, S3 GetObject = 5500 req/sec per prefix. Exceed them and AWS returns ThrottlingException. Fix: exponential backoff — growing delays between retries.

الـ SDK يُعيد المحاولةSDK retries

Java SDK v2 يُطبّق exponential backoff افتراضياً لأخطاء throttling و 5xx. لا تحتاج كتابته بنفسك غالباً.

Java SDK v2 applies exponential backoff by default for throttling and 5xx. You rarely need custom logic.

لا تعيد على 4xxDon't retry 4xx

أخطاء 400-499 تعني مشكلة في طلبك (صلاحيات، JSON غير صالح). إعادة المحاولة ستعطي نفس الخطأ.

400-499 errors mean your request is wrong (auth, bad JSON). Retrying gives the same error.

أعد على 5xx و 429Retry 5xx & 429

الـ 5xx أخطاء خادم مؤقّتة، 429 = throttling. كلاهما يُحَلّ بالصبر.

5xx are transient server errors, 429 = throttling. Both respond to patience.

Jitter مهمّJitter matters

أضِف عشوائية (jitter) للـ backoff لتجنّب "thundering herd" حيث كلّ الـ clients يُعيدون في نفس اللحظة.

Add randomization (jitter) to backoff to avoid the "thundering herd" where all clients retry simultaneously.

// Customize retry policy in Java SDK v2
import software.amazon.awssdk.core.retry.RetryPolicy;
import software.amazon.awssdk.core.retry.backoff.FullJitterBackoffStrategy;
import software.amazon.awssdk.services.s3.S3Client;
import software.amazon.awssdk.core.client.config.ClientOverrideConfiguration;

RetryPolicy retry = RetryPolicy.builder()
    .numRetries(5)                                                  // 5 retries
    .backoffStrategy(FullJitterBackoffStrategy.builder()
        .baseDelay(java.time.Duration.ofMillis(200))                // start at 200ms
        .maxBackoffTime(java.time.Duration.ofSeconds(20))           // cap at 20s
        .build())
    .build();

S3Client s3 = S3Client.builder()
    .overrideConfiguration(ClientOverrideConfiguration.builder()
        .retryPolicy(retry)
        .build())
    .build();

الحدود (Limits) و Service Quotas AWS Limits & Service Quotas

AWS تُطبّق نوعين من الحدود: API Rate Limits (عدد الاستدعاءات في الثانية)، و Service Quotas (الحدّ الأقصى لموارد الحساب، مثلاً 1152 vCPU للخوادم On-Demand). الأخيرة قابلة للرفع عبر Service Quotas API أو فتح تذكرة دعم.

AWS applies two kinds of limits: API Rate Limits (calls per second) and Service Quotas (max resources per account, e.g., 1152 vCPU for On-Demand). The latter can be raised via the Service Quotas API or by opening a support ticket.

نصيحة للامتحان:Exam tip: في الامتحان: إذا حصل الخطأ بشكل متقطّع → طبّق exponential backoff. إذا حصل بشكل مستمرّ → اطلب رفع الحدّ، فالتطبيق وصل حقيقةً لسقف الموارد. Exam tip: if the error is intermittent, apply exponential backoff. If persistent, request a quota increase — the app has truly hit the ceiling. 
// Inspect retries via SDK metrics (Java SDK v2)
import software.amazon.awssdk.metrics.MetricCollection;
import software.amazon.awssdk.metrics.MetricPublisher;

// Example: log number of retry attempts per call
MetricPublisher publisher = (MetricCollection collection) -> {
    collection.metricValues(software.amazon.awssdk.core.metrics.CoreMetric.RETRY_COUNT)
        .forEach(count -> System.out.println("Retries: " + count));
};

S3Client s3 = S3Client.builder()
    .overrideConfiguration(b -> b.addMetricPublisher(publisher))
    .build();
