الإتاحة العالية والتوسعة: ELB و Auto Scaling Groups High Availability & Scalability: ELB and Auto Scaling Groups

كيف تصمم طبقة تطبيقات تصمد أمام فشل AZ كاملة وتتوسّع مع الحِمل دون تدخّل يدويّ؟ الإجابة زوج لا ينفصل: Elastic Load Balancer يوزّع الطلبات، و Auto Scaling Group يضمن وجود العدد المطلوب من الخوادم السليمة. How do you build an application tier that survives a full-AZ outage and scales with load without manual intervention? The answer is an inseparable pair: Elastic Load Balancer distributes requests, Auto Scaling Group maintains the right number of healthy instances.

الفرق بين التوسعة العموديّة والأفقيّة والإتاحة العالية Vertical vs horizontal scaling vs High Availability

هذه ثلاثة مفاهيم يخلط الكثيرون بينها في الامتحان. التوسعة العموديّة (Vertical) تعني تكبير حجم الخادم الواحد. التوسعة الأفقيّة (Horizontal) تعني زيادة عدد الخوادم. الإتاحة العالية (High Availability) تعني توزيع النظام عبر عدّة AZs ليصمد أمام فشل إحداها.

Three concepts the exam loves to conflate. Vertical scaling = bigger instance. Horizontal scaling = more instances. High Availability = spread across multiple AZs to survive one AZ failure.

Vertical Scaling — Scale UpVertical — Scale Up

تكبير نفس الخادم (مثلاً t3.micro → r5.4xlarge). شائع للأنظمة غير الموزَّعة مثل قواعد البيانات. RDS و ElastiCache تتوسّع عموديّاً. الحدّ يفرضه أقصى حجم خادم (حالياً u-12tb1.metal بـ ١٢.٣ TB ذاكرة).

Bigger same instance (e.g., t3.micro → r5.4xlarge). Common for non-distributed systems like DBs. RDS and ElastiCache scale vertically. Limit = max instance size (currently u-12tb1.metal, 12.3 TB RAM).

Horizontal Scaling — Scale OutHorizontal — Scale Out

زيادة عدد الخوادم. مرونة (elasticity) حقيقيّة. يفترض أنّ التطبيق موزَّع (stateless أو state خارجيّ). يحقّقه Auto Scaling Group مع Load Balancer. حدّه هو حدود الحساب (حصص Service Quotas).

More instances. True elasticity. Requires a distributed (stateless or external-state) app. Achieved with Auto Scaling Group + Load Balancer. Limit is account quotas.

مفهوم أساسي:Key concept: الإتاحة العالية تأتي "مجاناً" مع التوسعة الأفقيّة إن وزّعت الخوادم عبر عدّة AZs. ASG + Multi-AZ + ELB = معمار HA كلاسيكيّ. لكن انتبه: Multi-AZ وحده لا يكفي إذا كانت جميع الخوادم في Region واحدة — لكارثة على مستوى Region تحتاج Multi-Region (موضوع Route 53). HA comes "for free" with horizontal scaling if you span multiple AZs. ASG + Multi-AZ + ELB = classic HA stack. But Multi-AZ alone doesn't protect against a Region-wide outage — that needs Multi-Region (Route 53 chapter).

أنواع Elastic Load Balancer الأربعة The 4 Elastic Load Balancer types

AWS تقدّم ٤ أنواع من الـ Load Balancer المُدار. الاختيار بينها يعتمد على طبقة OSI ونوع البروتوكول. الامتحان يسأل هذا كثيراً ضمن سيناريوهات الاختيار.

AWS offers 4 types of managed load balancers. The choice depends on OSI layer and protocol. The exam asks this in choice scenarios constantly.

ALB — ذكاء الطبقة ٧ALB — Layer 7 intelligence

يفهم محتوى HTTP. يوجّه بناءً على المسار (/users → backend A)، أو الـ hostname (api.acme.com)، أو Query String / Headers. ممتاز للـ microservices والـ containers (ECS/Fargate). يدعم WebSocket و redirects و Lambda كـ target. العميل لا يرى IP الخادم — يُضاف في X-Forwarded-For.

Understands HTTP content. Routes on path (/users → backend A), hostname (api.acme.com), or query string/headers. Ideal for microservices and containers (ECS/Fargate). Supports WebSocket, redirects, Lambda as target. Client IP not visible — passed via X-Forwarded-For.

NLB — السرعة الخامNLB — raw speed

يعمل على TCP/UDP مباشرةً. ملايين الطلبات في الثانية، زمن استجابة بالميكروثانية. يحصل على static IP لكلّ AZ، ويدعم Elastic IP — مفيد لحالات whitelisting العملاء. يمرّر IP العميل مباشرةً (لا يحتاج X-Forwarded-For).

Works directly on TCP/UDP. Millions RPS, microsecond latency. Static IP per AZ, supports Elastic IP — useful for client whitelisting. Preserves client IP directly (no X-Forwarded-For needed).

نصيحة للامتحان:Exam tip: الامتحان يربط الأنواع بحالات محدّدة: WebSocket/HTTP/2/redirect/path routing → ALB. IP ثابت/UDP/أداء قصوى → NLB. firewall/IDS من طرف ثالث → GWLB. Lambda targets يدعمها ALB فقط (NLB لا يدعم Lambda). Exam links types to specifics: WebSocket/HTTP/2/redirect/path routing → ALB. Static IP/UDP/extreme perf → NLB. 3rd-party firewall/IDS → GWLB. Lambda as target = ALB only (NLB doesn't support Lambda).

Target Groups وفحص الصحّة (Health Checks) Target Groups and Health Checks

الـ Load Balancer لا يرسل الطلبات مباشرةً إلى خوادم — بل إلى Target Group. كلّ Target Group يحدّد مجموعة من الأهداف (instances, IPs, Lambda, ALB nested) ومعاييرها للصحّة (health check). Load Balancer واحد يمكن أن يوجّه إلى عدّة Target Groups بناءً على قواعد التوجيه.

The LB doesn't send requests directly to instances — it sends them to a Target Group. Each Target Group defines targets (instances, IPs, Lambda, nested ALB) and health-check criteria. One LB can route to multiple Target Groups via routing rules.

EC2 InstancesEC2 Instances

الهدف الأكثر شيوعاً. يعمل مع ASG للـ elasticity.

Most common target. Pairs with ASG for elasticity.

IP AddressesIP Addresses

IPs خاصّة فقط. مفيد لأهداف on-premises عبر VPN/Direct Connect.

Private IPs only. Useful for on-premises targets via VPN/Direct Connect.

Lambda (ALB فقط)Lambda (ALB only)

HTTP يُترجَم إلى JSON event. خدمات serverless خلف ALB.

HTTP translated to JSON event. Serverless behind ALB.

ALB (لـ NLB)ALB (for NLB)

NLB يمكنه توجيه إلى ALB — مفيد لخلط أنماط HTTP و TCP.

NLB can target an ALB — useful for mixing HTTP + TCP patterns.

فحص الصحّة هو الكيفيّة التي يعرف بها LB إن كان الهدف جاهزاً لاستقبال الطلبات. يضبط على بروتوكول (HTTP/HTTPS/TCP)، منفذ، ومسار (شائع /health). استجابة خارج نطاق 200-399 → unhealthy → يتوقّف إرسال الطلبات.

Health checks are how the LB knows a target is ready. Configured per protocol (HTTP/HTTPS/TCP), port, and path (/health common). Response outside 200-399 → unhealthy → traffic stops.

// Spring Boot health endpoint — standard pattern
@RestController
public class HealthController {

    private final DataSource ds;
    private final RedisTemplate<String,String> redis;

    public HealthController(DataSource ds, RedisTemplate<String,String> redis) {
        this.ds = ds;
        this.redis = redis;
    }

    // Shallow check — for ALB target group health
    @GetMapping("/health")
    public ResponseEntity<Map<String,String>> health() {
        return ResponseEntity.ok(Map.of("status", "UP"));
    }

    // Deep check — for internal monitoring (DO NOT use for ALB)
    // Using deep checks for ALB causes cascading failures when DB is slow
    @GetMapping("/health/deep")
    public ResponseEntity<?> deep() {
        try (var conn = ds.getConnection()) {
            conn.isValid(1);
            redis.opsForValue().get("healthcheck");
            return ResponseEntity.ok(Map.of("status", "UP"));
        } catch (Exception e) {
            return ResponseEntity.status(503).body(Map.of("status", "DOWN"));
        }
    }
}
للمطوّر السينيور:For the senior dev: فخّ كلاسيكيّ للـ seniors: جعل /health يفحص قاعدة البيانات و Redis يتسبّب في cascading failure. عند بطء قاعدة البيانات، كلّ الخوادم تفشل في الـ health check، فتُخرَج من ALB → يصبح النظام كلّه down. اجعل /health للـ ALB سطحياً (liveness)، والفحص العميق (readiness) لأدوات المراقبة الداخلية فقط. Classic senior pitfall: making /health hit the DB and Redis causes cascading failure. When the DB slows, every instance fails the health check and ALB pulls them all → full outage. Keep /health shallow (liveness) for ALB; deep (readiness) goes to internal monitoring only.

Sticky Sessions و Cross-Zone Load Balancing Sticky Sessions and Cross-Zone Load Balancing

Sticky Sessions (Session Affinity) تجعل طلبات مستخدم معيّن تعود دائماً إلى نفس الخادم. مفيد لتطبيقات لا تضع حالة الجلسة في مخزن مشترك. تعمل عبر cookie (ALB/CLB) أو hash على 5-tuple (NLB).

Sticky Sessions pin a user's requests to the same instance. Useful when session state isn't in a shared store. Works via cookie (ALB/CLB) or 5-tuple hash (NLB).

فخّ شائع:Common pitfall: أسماء الـ cookies محجوزة: AWSALB, AWSALBAPP, AWSALBTG ممنوعة للـ custom cookies. Stickiness ممكن أن يسبّب عدم توازن في الحِمل على الخوادم الخلفية — خوادم قليلة قد تستقبل معظم الحِمل إذا كانت جلسات المستخدمين طويلة. Reserved cookie names: AWSALB, AWSALBAPP, AWSALBTG are forbidden for custom. Stickiness can cause backend imbalance — a few instances may get most traffic if user sessions are long.

With Cross-Zone LBWith Cross-Zone LB

كلّ عقدة LB في كلّ AZ توزّع على كلّ الخوادم في كلّ AZs. التوزيع متساوٍ حتى لو كان عدد الخوادم مختلف بين AZs. ALB: مُفعَّل افتراضياً، لا رسوم بين AZs. NLB/GWLB: مُعطَّل افتراضياً، رسوم بين AZs عند التفعيل.

Each LB node in each AZ distributes across all instances in all AZs. Even distribution regardless of uneven AZ capacity. ALB: enabled by default, no inter-AZ charges. NLB/GWLB: disabled by default, inter-AZ charges when enabled.

Without Cross-Zone LBWithout Cross-Zone LB

عقدة LB في كلّ AZ توزّع فقط على خوادم نفس الـ AZ. يؤدّي إلى توزيع غير متوازن إذا كان عدد الخوادم مختلف. مثال: AZ1 بخادمين يستقبل ٥٠٪ من الحِمل، AZ2 بأربعة يستقبل ٥٠٪ — الخادم في AZ1 يعمل ضعف الخادم في AZ2.

Each LB node in an AZ routes only to that AZ's instances. Creates imbalance if AZ counts differ. Example: AZ1 (2 instances) gets 50%, AZ2 (4) gets 50% — AZ1 instance works 2× harder.

Auto Scaling Group (ASG) وسياسات التوسعة Auto Scaling Groups (ASG) and scaling policies

ASG يضمن أنّ لديك دائماً عدد الخوادم الذي تحتاجه. يُعرَّف بـ Launch Template (AMI، نوع الخادم، User Data، Security Groups، IAM Role، ...) و حدود Min/Desired/Max. عند فشل خادم (failed health check) يستبدله ASG تلقائياً. ASG نفسه مجاني — تدفع فقط للخوادم.

ASG ensures you always have the number of instances you need. Defined by a Launch Template (AMI, instance type, User Data, SGs, IAM Role, ...) and Min/Desired/Max bounds. On instance failure, ASG replaces it automatically. ASG itself is free — you only pay for instances.

// Java SDK v2 — create an ASG with a Target Tracking policy
import software.amazon.awssdk.services.autoscaling.AutoScalingClient;
import software.amazon.awssdk.services.autoscaling.model.*;

AutoScalingClient asg = AutoScalingClient.create();

// 1. Create the ASG (Launch Template assumed pre-existing)
asg.createAutoScalingGroup(CreateAutoScalingGroupRequest.builder()
    .autoScalingGroupName("acme-web-asg")
    .launchTemplate(LaunchTemplateSpecification.builder()
        .launchTemplateId("lt-0abc123").version("$Latest").build())
    .minSize(2).desiredCapacity(4).maxSize(10)
    .vpcZoneIdentifier("subnet-a,subnet-b,subnet-c") // 3 AZs for HA
    .targetGroupARNs("arn:aws:elasticloadbalancing:...:targetgroup/acme-tg/...")
    .healthCheckType("ELB") // use ALB health checks, not only EC2
    .healthCheckGracePeriod(120) // grace period for app warmup
    .build());

// 2. Attach a Target Tracking policy — keep CPU around 50%
asg.putScalingPolicy(PutScalingPolicyRequest.builder()
    .autoScalingGroupName("acme-web-asg")
    .policyName("cpu-at-50")
    .policyType("TargetTrackingScaling")
    .targetTrackingConfiguration(TargetTrackingConfiguration.builder()
        .predefinedMetricSpecification(p -> p.predefinedMetricType(
            MetricType.ASG_AVERAGE_CPU_UTILIZATION))
        .targetValue(50.0)
        .build())
    .build());

Cooldown (default 300s)Cooldown (default 300s)

بعد كلّ عمليّة توسعة، ASG ينتظر ٥ دقائق قبل عمليّة أخرى. لا تقلّله إلى أقلّ من زمن بدء تشغيل الخادم.

After each scaling action, ASG waits 5 min before the next. Don't set it lower than instance warm-up time.

نصيحة:Tip: Instance Refresh (ميزة ASG) تسمح بتحديث launch template ثمّ إعادة إنشاء كلّ الخوادم بنسبة صحّية دنيا (Min Healthy Percentage). طريقة رسميّة لتطبيق rolling updates بدون down-time — بديل rolling CodeDeploy عندما لا تحتاج تعقيداته. Instance Refresh (ASG feature) lets you update the launch template and re-create all instances respecting a minimum healthy percentage. The official no-downtime rolling update — a leaner alternative to CodeDeploy rolling when you don't need its complexity.

Security Groups و Connection Draining Security Groups and Connection Draining

النمط المعياريّ: Security Group لـ Load Balancer يسمح بـ HTTP/HTTPS من الإنترنت (0.0.0.0/0). Security Group للخوادم خلفه يسمح فقط بحركة من Security Group الـ LB (لا من IP الإنترنت). هذه هي الطريقة الصحيحة لـ isolation.

Canonical pattern: LB Security Group allows HTTP/HTTPS from the Internet (0.0.0.0/0). Backend SG allows only traffic from the LB's SG (not from Internet IPs). This is the correct isolation pattern.

# LB Security Group: accept from anyone
aws ec2 authorize-security-group-ingress \
  --group-id sg-lb-0abc --protocol tcp --port 443 --cidr 0.0.0.0/0

# Backend Security Group: accept only from LB's SG (NOT from Internet)
aws ec2 authorize-security-group-ingress \
  --group-id sg-app-0xyz --protocol tcp --port 8080 \
  --source-group sg-lb-0abc

Connection Draining (CLB) / Deregistration Delay (ALB/NLB) هو الوقت الذي تنتظره LB للطلبات الجارية على خادم يُحذَف قبل قطع الاتّصال. الافتراضي ٣٠٠ ثانية، المدى ١-٣٦٠٠. ضع قيمة منخفضة (٢٠-٣٠ ثانية) إن كانت طلباتك قصيرة.

Connection Draining (CLB) / Deregistration Delay (ALB/NLB) is the time the LB waits for in-flight requests on a deregistering instance before closing. Default 300s, range 1-3600. Set low (20-30s) if your requests are short.

نصيحة للامتحان:Exam tip: عند استخدام SSL/TLS على ALB/NLB: خدمة ACM (Certificate Manager) توفّر الشهادات مجاناً مع تجديد تلقائيّ. SNI (Server Name Indication) يسمح بعدّة شهادات على نفس الـ listener — مدعوم في ALB و NLB، لكن غير مدعوم في CLB. For SSL/TLS on ALB/NLB: ACM (Certificate Manager) provides free auto-renewing certs. SNI (Server Name Indication) allows multiple certs on one listener — supported in ALB and NLB, not in CLB.
