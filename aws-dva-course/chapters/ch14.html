لماذا فكّ الاقتران ومتى تستخدم أيّ خدمة Why decouple and when to use each service

بدلاً من اتّصال synchronous (تطبيق يستدعي آخر مباشرة)، نستخدم وسيطاً بينهما. الفائدة: الخدمتان تتوسّعان مستقلّتَين، والفشل في إحداهما لا يسقط الأخرى، والنمط الأول يناسب البنى event-driven الحديثة. AWS تُقدّم أربع أدوات لهذا الغرض، وكلٌّ له استخدامه.

Instead of synchronous calls (app A directly invokes app B), insert a middleman. Benefits: both scale independently, failure in one doesn't cascade, and the pattern fits modern event-driven designs. AWS offers four tools, each with its niche.

Amazon SQS — القائمة المعيارية Amazon SQS — the standard queue

SQS خدمة queue مُدارة بالكامل. المنتج يرسل رسائل بحجم حتى ٢٥٦ KB (١ KB في الفوترة، ١٠٢٤ KB حدّ الإرسال)، وتُحفَظ لمدّة افتراضية ٤ أيام (حتى ١٤). المستهلك يسحب (pull) الرسائل ويحذفها بعد المعالجة.

SQS is a fully managed queue. Producers send messages up to 256 KB (1 KB billing unit, 1024 KB send limit), retained 4 days by default (up to 14). Consumers poll messages and delete after processing.

Standard QueueStandard Queue

إنتاجية غير محدودة. At-least-once delivery (قد تتكرّر الرسائل). Best-effort ordering (قد تأتي خارج الترتيب). الأكثر استخداماً.

Unlimited throughput. At-least-once delivery (possible duplicates). Best-effort ordering. The default choice.

FIFO QueueFIFO Queue

إنتاجية ٣٠٠ رسالة/ثانية (٣٠٠٠ مع batching، عالية الإنتاجية). Exactly-once و strict ordering. الاسم ينتهي بـ .fifo.

300 msg/sec (3000 batched, high-throughput). Exactly-once and strict ordering. Queue name must end with .fifo.

Visibility TimeoutVisibility Timeout

بعد pull، الرسالة تختفي لمدّة ٣٠ ثانية (افتراضي، ٠ – ١٢ ساعة). إن لم تُحذَف خلال الوقت، تعود للقائمة. ChangeMessageVisibility لتمديد الوقت.

After polling, message is hidden for 30s (default, 0 – 12h). If not deleted in time, it returns to the queue. Use ChangeMessageVisibility to extend.

Dead Letter QueueDead Letter Queue

بعد MaxReceives محاولات فاشلة، الرسالة تنتقل لـ DLQ. DLQ لـ FIFO يجب أن تكون FIFO أيضاً. يُفضَّل احتفاظ ١٤ يوماً للتحقيق.

After MaxReceives failed attempts, the message moves to DLQ. FIFO DLQ must also be FIFO. Set 14-day retention for investigation.

Delay QueueDelay Queue

تأخير ظهور الرسائل للمستهلك حتى ١٥ دقيقة (queue level)، أو per-message بـ DelaySeconds.

Delay message visibility up to 15 min (queue level), or per-message via DelaySeconds.

Long PollingLong Polling

بدل short polling الذي يُهدر API calls، الـ ReceiveMessageWaitTimeSeconds ينتظر حتى ٢٠ ثانية لوصول رسالة. مفضَّل دائماً.

Instead of short polling (wasteful), ReceiveMessageWaitTimeSeconds waits up to 20s for a message. Always preferred.

// Java SDK v2 — send & receive from SQS
import software.amazon.awssdk.services.sqs.SqsClient;
import software.amazon.awssdk.services.sqs.model.*;

SqsClient sqs = SqsClient.create();
String url = "https://sqs.us-east-1.amazonaws.com/123/orders";

// Send
sqs.sendMessage(b -> b.queueUrl(url)
    .messageBody("{\"orderId\":42}")
    .delaySeconds(10));          // delay up to 900s

// Receive with long polling + batch of 10
ReceiveMessageResponse resp = sqs.receiveMessage(b -> b
    .queueUrl(url)
    .maxNumberOfMessages(10)       // 1-10
    .waitTimeSeconds(20));         // long poll

for (Message m : resp.messages()) {
    process(m.body());
    sqs.deleteMessage(d -> d.queueUrl(url).receiptHandle(m.receiptHandle()));
}
نصيحة:Tip: SQS Extended Client Library (Java) يحلّ مشكلة الـ ٢٥٦ KB limit: يضع الـ payload الكبير في S3 ويرسل مرجعاً في SQS. لكن الامتحان يسأل عادة عن الحدّ الأصلي. SQS Extended Client Library (Java) solves the 256 KB limit by storing large payloads in S3 and sending a reference via SQS. Exam usually asks about the raw limit.

Amazon SNS — النشر والاشتراك Amazon SNS — publish & subscribe

SNS هو pub/sub: ناشر يرسل رسالة إلى Topic، والخدمة تُسلّمها إلى كل Subscribers. كل subscriber يستقبل نسخة. الاستخدام الشهير: fan-out pattern مع عدّة SQS queues.

SNS is pub/sub: a publisher sends to a Topic, and the service delivers to every Subscriber. Each subscriber gets a copy. Classic use: fan-out pattern with multiple SQS queues.

أنواع المشتركينSubscriber types

SQS، Lambda، HTTP/HTTPS endpoint، Email، SMS، Mobile push، Kinesis Data Firehose.

SQS, Lambda, HTTP/HTTPS endpoint, Email, SMS, Mobile push, Kinesis Data Firehose.

Fan-out PatternFan-out Pattern

SNS Topic → عدّة SQS queues. كل queue يعالج بشكل مستقلّ ومتوازٍ. نمط شائع جداً في الامتحان.

SNS Topic → multiple SQS queues. Each queue processes independently, in parallel. Very common exam pattern.

Filter PoliciesFilter Policies

كل subscriber يستقبل فقط الرسائل التي تطابق filter policy بناءً على message attributes. JSON format.

Each subscriber receives only messages matching its filter policy on message attributes. JSON format.

FIFO TopicsFIFO Topics

ترتيب صارم، مثل SQS FIFO. فقط subscribers من نوع SQS FIFO. .fifo suffix.

Strict ordering, like SQS FIFO. Only SQS FIFO subscribers. .fifo suffix.

// SNS Filter Policy — subscriber gets messages only for 'premium' customers in 'US'
{
  "customerType": ["premium"],
  "region":       ["US", "CA"]
}

// Publisher sends with message attributes:
// { "customerType": "premium", "region": "US" } → delivered
// { "customerType": "free",    "region": "US" } → filtered out

Amazon Kinesis — تدفّق البيانات الفوري Amazon Kinesis — real-time data streaming

Kinesis عائلة من ٣ خدمات للتدفّق: Data Streams (streaming خام)، Data Firehose (تحميل لـ S3/Redshift/OpenSearch)، Data Analytics (حالياً Managed Service for Apache Flink). الاختيار بينها سؤال متكرّر في الامتحان.

Kinesis is a 3-service family: Data Streams (raw streaming), Data Firehose (load to S3/Redshift/OpenSearch), Data Analytics (now Managed Service for Apache Flink). Picking among them is a frequent exam question.

الخدمةServiceالوصفDescriptionالتسعيرPricingReal-time?Real-time?
Data StreamsData Streamsshards تدويّة، احتفاظ حتى سنة، KCL للقراءةManual shards, up to 1-year retention, KCL consumersper shard/hourPer shard/hourنعم (٢٠٠ ms)Yes (~200 ms)
Data FirehoseData Firehoseتحميل مُدار إلى S3 / Redshift / OpenSearch / HTTPManaged load to S3 / Redshift / OpenSearch / HTTPper GB محمّلPer GB loadedNear real-time (٦٠ s buffer)Near real-time (60s buffer)
Managed FlinkManaged Flinkتحليل الـ stream بـ SQL/Apache FlinkStream analytics with SQL/Apache Flinkper KPUPer KPUنعمYes

في Data Streams: البيانات تنقسم على shards. كل shard يدعم ١ MB/s ingest و ٢ MB/s read، أو ١٠٠٠ rec/s. المنتج يستخدم Partition Key يُحدّد الـ shard. عدّة مستهلكين يقرأون نفس البيانات (replayable). KCL (Kinesis Client Library) يسهّل بناء consumer موزّع.

In Data Streams: data is sharded. Each shard supports 1 MB/s ingest, 2 MB/s read, or 1000 rec/s. Producers use a Partition Key to pick a shard. Multiple consumers can read the same data (replayable). KCL (Kinesis Client Library) simplifies building distributed consumers.

فخّ شائع:Common pitfall: خطأ ProvisionedThroughputExceededException في Kinesis غالباً بسبب hot shard — partition key سيّئ. الحلول: توزيع أفضل للـ partition keys، أو زيادة الـ shards (resharding)، أو التحوّل إلى On-Demand mode. ProvisionedThroughputExceededException in Kinesis usually = hot shard from a bad partition key. Fixes: better key distribution, reshard (split), or switch to On-Demand mode.

Kinesis Data StreamsKinesis Data Streams

للبيانات الخام: تطبيقات تحتاج replay، تعدّد المستهلكين، معالجة مخصّصة. أنت تديره (shards).

For raw data: apps needing replay, multiple consumers, custom processing. You manage (shards).

Kinesis Data FirehoseKinesis Data Firehose

للتحميل التلقائي: S3 أو Redshift أو OpenSearch. لا shards، لا KCL. يحوّل ويضغط البيانات تلقائياً.

For auto-load: S3, Redshift, OpenSearch. No shards, no KCL. Transforms/compresses automatically.

Amazon EventBridge — ناقل الأحداث Amazon EventBridge — event bus

EventBridge (سابقاً CloudWatch Events) هو event bus بيانيّ بين خدمات AWS، تطبيقاتك، وبرامج SaaS. خدمات AWS ترسل أحداثها تلقائياً للـ default event bus. القواعد (Rules) تحدّد أيّ أحداث تُرسل إلى أيّ targets (Lambda, SQS, SNS, Step Functions, Kinesis...).

EventBridge (formerly CloudWatch Events) is a graph-shaped event bus between AWS services, your apps, and SaaS. AWS services auto-publish events to the default event bus. Rules match events and route to targets (Lambda, SQS, SNS, Step Functions, Kinesis...).

أنواع Event BusesBus types

Default (أحداث AWS)، Custom (أحداث تطبيقك)، Partner (SaaS مثل Shopify, Datadog).

Default (AWS events), Custom (your app), Partner (SaaS: Shopify, Datadog).

Event PatternEvent Pattern

JSON يطابق الأحداث بناءً على source, detail-type, fields. دعم operators (exists, prefix, numeric, anything-but).

JSON matching events by source, detail-type, fields. Operators: exists, prefix, numeric, anything-but.

Schedule ExpressionsSchedule Expressions

cron (cron(0 12 * * ? *)) أو rate (rate(5 minutes)). بديل لـ cron jobs التقليدية.

cron (cron(0 12 * * ? *)) or rate (rate(5 minutes)). Replaces traditional cron jobs.

Schema RegistrySchema Registry

EventBridge يكتشف schemas للأحداث تلقائياً ويولّد code bindings (Java/Python/TypeScript).

EventBridge auto-discovers event schemas and generates code bindings (Java/Python/TypeScript).

// EventBridge rule: trigger Lambda on S3 object creation in 'uploads/' prefix
{
  "source": ["aws.s3"],
  "detail-type": ["Object Created"],
  "detail": {
    "bucket": { "name": ["my-uploads"] },
    "object": { "key": [{ "prefix": "uploads/" }] }
  }
}

// Custom event sent by your app via PutEvents
{
  "Source": "com.acme.orders",
  "DetailType": "OrderPlaced",
  "Detail": "{\"orderId\":\"o-42\",\"total\":199.0}",
  "EventBusName": "acme-orders"
}
للمطوّر السينيور:For the senior dev: للسينيور: EventBridge بديل أنظف من SNS لـ event-driven microservices داخل AWS — يوفّر schema discovery، filtering بـ JSON pattern بدلاً من attributes، و archive/replay مدمج. اختر SNS للـ fan-out البسيط والـ Email/SMS، و EventBridge للنمط event-driven الحقيقي. Senior take: EventBridge is a cleaner SNS alternative for event-driven microservices inside AWS — schema discovery, JSON-pattern filtering (vs attributes), and built-in archive/replay. Pick SNS for simple fan-out or Email/SMS, EventBridge for proper event-driven design.
