ما هي DynamoDB ومفاهيم أساسية What is DynamoDB & core concepts

DynamoDB قاعدة بيانات NoSQL مُدارة بالكامل من AWS، تدعم النسخ التلقائي بين مناطق التوفّر، وتقدّم زمن استجابة ثابت بأجزاء من الألف من الثانية على أيّ مقياس — ملايين الطلبات في الثانية وتريليونات الصفوف ومئات التيرابايت. هي الخيار المعياريّ لتطبيقات Lambda + API Gateway لأنّها serverless بطبيعتها.

DynamoDB is AWS's fully managed NoSQL database with automatic multi-AZ replication. It offers consistent single-digit millisecond latency at any scale — millions of requests/sec, trillions of rows, 100s of TB. It's the default pick for Lambda + API Gateway stacks because it's inherently serverless.

جداول (Tables)Tables

كل جدول يحتاج Primary Key يُحدّد عند الإنشاء. عدد العناصر غير محدود.

Every table needs a Primary Key defined at creation. Items per table are unlimited.

عناصر (Items)Items

يعادل الصف في SQL. الحدّ الأقصى لحجم العنصر ٤٠٠ كيلوبايت.

Equivalent to a row in SQL. Max item size is 400 KB.

سمات (Attributes)Attributes

كل عنصر يحتوي سمات قابلة للإضافة بمرور الوقت. Schema-less بعد المفتاح.

Each item has attributes you can add over time. Schema-less beyond the key.

أنواع البياناتData Types

Scalar: String, Number, Binary, Boolean, Null. Document: List, Map. Set: String/Number/Binary Set.

Scalar: String, Number, Binary, Boolean, Null. Document: List, Map. Set: String/Number/Binary Set.

مفهوم أساسي:Key concept: DynamoDB لا تدعم joins ولا aggregations (SUM/AVG). يجب تصميم البيانات بحيث تكون كل بيانات الاستعلام في صفّ واحد. هذا مفهوم single-table design. DynamoDB has no joins and no aggregations (SUM/AVG). Model your data so all data for a query lives in one row — that's single-table design.

Primary Keys و Partitions والـ Hot Keys Primary Keys, Partitions, and Hot Keys

للـ Primary Key خياران: Partition Key وحده (HASH) حيث يجب أن يكون فريداً لكل عنصر، أو Partition Key + Sort Key (HASH + RANGE) حيث يجب أن تكون الـ combination فريدة. البيانات تُجمَّع فيزيائياً حسب الـ Partition Key ويتم فرزها داخلياً حسب الـ Sort Key.

Primary Key has two options: Partition Key alone (HASH) which must be unique per item, or Partition Key + Sort Key (HASH + RANGE) where the combination must be unique. Data is physically grouped by Partition Key and sorted internally by Sort Key.

Partition Key جيّدGood Partition Key

قيمة ذات cardinality عالية وتوزيع متساوٍ. مثال: user_id, order_id, UUID. توزّع الحِمل بين الـ partitions بالتساوي.

High cardinality, evenly distributed. Example: user_id, order_id, UUID. Spreads load evenly across partitions.

Partition Key سيّئ (Hot Key)Bad Partition Key (Hot Key)

قيم قليلة أو منحازة. مثال: country (معظم الطلبات سيضرب US)، status (قيم قليلة). يسبّب ProvisionedThroughputExceededException.

Low-cardinality or skewed. Example: country (most hit US), status (few values). Causes ProvisionedThroughputExceededException.

البيانات تُخزَّن في partitions داخلية تديرها AWS. الـ Partition Key يمر على hashing algorithm ليُحدَّد الـ partition الذي سيخزَّن فيه. الـ WCU و RCU توزَّعان بالتساوي بين الـ partitions، فإن ضربت كل الطلبات partition واحد ستحصل على throttling حتى لو كانت الـ capacity الكلّية كبيرة.

Data is stored in internal partitions managed by AWS. The Partition Key is hashed to determine which partition holds the item. WCU and RCU are split evenly across partitions — if all your traffic hits one partition, you'll be throttled even when total capacity is high.

فخّ شائع:Common pitfall: حلول الـ Hot Partition: (١) Write Sharding — أضف suffix عشوائي أو محسوب للـ Partition Key لتوزيع الكتابة. (٢) DAX لحلّ Hot Keys في القراءة. (٣) Exponential backoff في الـ SDK (موجود تلقائياً). (٤) استخدم On-Demand mode إن كانت الأحمال غير متوقّعة. Hot Partition fixes: (1) Write Sharding — add random or calculated suffix to the Partition Key to spread writes. (2) DAX for read-side Hot Keys. (3) Exponential backoff in SDK (already built-in). (4) Switch to On-Demand mode for unpredictable workloads. 
// Java SDK v2 — Enhanced DynamoDB Client with partition + sort key
import software.amazon.awssdk.enhanced.dynamodb.*;
import software.amazon.awssdk.services.dynamodb.DynamoDbClient;

DynamoDbEnhancedClient enhanced = DynamoDbEnhancedClient.builder()
    .dynamoDbClient(DynamoDbClient.create())
    .build();

DynamoDbTable<Order> orders = enhanced.table("Orders",
    TableSchema.fromBean(Order.class));

// Query items for a given userId (partition key) with orderId > 100 (sort key)
QueryConditional q = QueryConditional.sortGreaterThan(
    Key.builder().partitionValue("user-42").sortValue(100).build());

orders.query(r -> r.queryConditional(q).limit(25))
      .items().forEach(System.out::println);

Capacity Modes: Provisioned vs On-Demand Capacity Modes: Provisioned vs On-Demand

لكل جدول وضعان لإدارة الإنتاجية. Provisioned: تحدّد RCU/WCU مقدّماً وتدفع للـ capacity المحجوز. On-Demand: تدفع مقابل الاستخدام الفعلي (RRU/WRU). يمكن التبديل بينهما مرّة كل ٢٤ ساعة.

Each table has two capacity modes. Provisioned: specify RCU/WCU upfront, pay for reserved capacity. On-Demand: pay for actual use (RRU/WRU). Switching modes is allowed once every 24 hours.

نصيحة للامتحان:Exam tip: ١ WCU = كتابة واحدة بالثانية لعنصر حتى ١ KB. ١ RCU = قراءة متّسقة قوية (Strongly Consistent) لعنصر حتى ٤ KB بالثانية، أو قراءتان Eventually Consistent. الأحجام تُقرَّب للأعلى. القراءة المتّسقة قوية تستهلك ضعف الـ RCU. 1 WCU = 1 write/sec for items up to 1 KB. 1 RCU = 1 Strongly Consistent read/sec up to 4 KB, or 2 Eventually Consistent reads. Sizes round up. Strongly Consistent reads cost 2× the RCU. 
// Strongly Consistent Read — pass consistentRead(true)
GetItemResponse resp = ddb.getItem(b -> b
    .tableName("Orders")
    .key(Map.of("orderId", AttributeValue.fromS("o-42")))
    .consistentRead(true));      // doubles RCU cost

// Eventually Consistent Read (default) — ~half the cost
GetItemResponse eventual = ddb.getItem(b -> b
    .tableName("Orders")
    .key(Map.of("orderId", AttributeValue.fromS("o-42"))));

Queries و Scans و Conditional Writes و PartiQL Queries, Scans, Conditional Writes & PartiQL

عمليات القراءة الأساسية: GetItem (على الـ Primary Key)، Query (على Partition Key + شرط Sort Key)، Scan (يقرأ الجدول كله — مكلف). BatchGetItem يقرأ حتى ١٠٠ عنصر من جداول متعدّدة.

Core read operations: GetItem (on Primary Key), Query (on Partition Key + Sort Key condition), Scan (reads entire table — expensive). BatchGetItem reads up to 100 items across multiple tables.

Query (مُفضَّل)Query (preferred)

يتطلّب Partition Key (= operator)، مع شرط اختياري على Sort Key (=, <, >, between, begins_with). يعيد حتى ١ MB أو حسب Limit.

Requires Partition Key (= operator), optional Sort Key condition (=, <, >, between, begins_with). Returns up to 1 MB or per Limit.

Scan (مكلف)Scan (expensive)

يقرأ الجدول كلّه ثم يفلتر. يستهلك RCU كثيراً. استخدم Parallel Scan للسرعة، و Limit/FilterExpression للتحكّم.

Reads whole table then filters. Burns RCU. Use Parallel Scan for speed, Limit/FilterExpression for control.

Conditional Writes: تقبل الـ Put/Update/Delete فقط إذا تحقّق شرط (attribute_exists, attribute_not_exists, contains, begins_with, size, IN, between). تُستخدم لـ Optimistic Locking ومنع استبدال البيانات غير المقصود.

Conditional Writes: accept Put/Update/Delete only if a condition holds (attribute_exists, attribute_not_exists, contains, begins_with, size, IN, between). Used for Optimistic Locking and preventing accidental overwrites.

// Conditional Update — only decrement stock if current > 0
UpdateItemResponse resp = ddb.updateItem(b -> b
    .tableName("Inventory")
    .key(Map.of("sku", AttributeValue.fromS("ABC-123")))
    .updateExpression("SET stock = stock - :qty")
    .conditionExpression("stock >= :qty")
    .expressionAttributeValues(Map.of(
        ":qty", AttributeValue.fromN("1"))));

// Optimistic Locking pattern — only update if version matches
ddb.updateItem(b -> b
    .tableName("Orders").key(key)
    .updateExpression("SET #s = :new, version = version + :one")
    .conditionExpression("version = :current")
    .expressionAttributeNames(Map.of("#s", "status"))
    .expressionAttributeValues(Map.of(
        ":new",     AttributeValue.fromS("SHIPPED"),
        ":current", AttributeValue.fromN("3"),
        ":one",     AttributeValue.fromN("1"))));
نصيحة:Tip: PartiQL هو SQL-compatible query language لـ DynamoDB. يدعم SELECT, INSERT, UPDATE, DELETE (لا يدعم كل SQL). مفيد للمطوّرين القادمين من عالم SQL مثلك. PartiQL is a SQL-compatible query language for DynamoDB. Supports SELECT, INSERT, UPDATE, DELETE (not full SQL). Useful for devs coming from SQL backgrounds like yours.

الفهارس: GSI vs LSI Indexes: GSI vs LSI

الفهارس تُمكّنك من الاستعلام بأنماط مختلفة عن الـ Primary Key. نوعان: LSI (Local Secondary Index) و GSI (Global Secondary Index). الفرق بينهما من أهمّ مواضيع الامتحان.

Indexes let you query using patterns other than the Primary Key. Two types: LSI (Local Secondary Index) and GSI (Global Secondary Index). Their differences are heavily exam-tested.

فخّ شائع:Common pitfall: خطر GSI: لو كانت الكتابات على الـ GSI مختنقة (throttled)، فإنّ الجدول الرئيسي كله سيختنق أيضاً — حتى لو كانت WCU للجدول كافية. اختر Partition Key للـ GSI بعناية وخصّص WCU كافية. الـ LSI يستخدم نفس الـ capacity بلا مشاكل. GSI gotcha: if writes to the GSI are throttled, the main table throttles too — even if table WCU is fine. Choose your GSI partition key carefully and provision enough WCU. LSI uses the table's capacity without this problem. 
# Create a GSI on an existing table (no downtime)
aws dynamodb update-table \
  --table-name Orders \
  --attribute-definitions \
      AttributeName=customerId,AttributeType=S \
      AttributeName=orderDate,AttributeType=S \
  --global-secondary-index-updates \
    '[{"Create":{"IndexName":"byCustomer",
        "KeySchema":[{"AttributeName":"customerId","KeyType":"HASH"},
                     {"AttributeName":"orderDate","KeyType":"RANGE"}],
        "Projection":{"ProjectionType":"ALL"},
        "ProvisionedThroughput":{"ReadCapacityUnits":5,"WriteCapacityUnits":5}}}]'

DAX و Streams و TTL و Transactions DAX, Streams, TTL & Transactions

DAX — كاش DynamoDBDAX — DynamoDB cache

in-memory cache بـ microseconds latency. متوافق ١٠٠٪ مع DynamoDB API (بدون تغيير الكود). TTL افتراضي ٥ دقائق. يحلّ مشكلة Hot Keys في القراءة. حتى ١٠ nodes في الـ cluster.

In-memory cache with microseconds latency. 100% DynamoDB-API compatible (no code changes). Default TTL 5 minutes. Solves read-side Hot Keys. Up to 10 nodes per cluster.

Streams — تدفّق التعديلاتStreams — change feed

تدفّق مُرتَّب لكل create/update/delete. يُقرأ بواسطة Lambda أو KCL. خيارات: KEYS_ONLY / NEW_IMAGE / OLD_IMAGE / NEW_AND_OLD_IMAGES. احتفاظ ٢٤ ساعة.

Ordered feed of create/update/delete. Read via Lambda or KCL. Options: KEYS_ONLY / NEW_IMAGE / OLD_IMAGE / NEW_AND_OLD_IMAGES. 24-hour retention.

TTL — حذف تلقائيTTL — auto delete

يحذف العناصر بعد timestamp محدّد (Unix epoch). لا يستهلك WCU. يحذف من الـ indexes أيضاً. مفيد للجلسات والبيانات المؤقتة.

Deletes items after a given timestamp (Unix epoch). Consumes no WCU. Also deletes from indexes. Great for sessions and temp data.

Transactions — ACIDTransactions — ACID

All-or-nothing عبر عدّة جداول. TransactGetItems و TransactWriteItems. تستهلك ضعف الـ WCU/RCU (prepare + commit).

All-or-nothing across tables. TransactGetItems and TransactWriteItems. Consumes 2× WCU/RCU (prepare + commit).

للمطوّر السينيور:For the senior dev: كمطوّر Spring Boot سينيور: عند حاجتك لـ SAGA pattern أو تزامن عبر microservices، استخدم DynamoDB Streams مع Lambda بدل Kafka لتوفير البنية التحتية. وللـ Idempotency (مطلب شائع في المدفوعات)، استخدم Conditional Writes بـ attribute_not_exists(idempotency_key). Senior Spring Boot dev tip: for SAGA patterns or microservice synchronization, use DynamoDB Streams + Lambda instead of Kafka — zero infra. For idempotency (common in payments), use Conditional Writes with attribute_not_exists(idempotency_key). 
// TransactWriteItems: atomically move money between two accounts
TransactWriteItemsRequest tx = TransactWriteItemsRequest.builder()
  .transactItems(
    TransactWriteItem.builder().update(Update.builder()
      .tableName("Accounts").key(Map.of("id", AttributeValue.fromS("A")))
      .updateExpression("SET balance = balance - :amt")
      .conditionExpression("balance >= :amt")
      .expressionAttributeValues(Map.of(":amt", AttributeValue.fromN("100")))
      .build()).build(),
    TransactWriteItem.builder().update(Update.builder()
      .tableName("Accounts").key(Map.of("id", AttributeValue.fromS("B")))
      .updateExpression("SET balance = balance + :amt")
      .expressionAttributeValues(Map.of(":amt", AttributeValue.fromN("100")))
      .build()).build())
  .build();

ddb.transactWriteItems(tx);  // atomic — both succeed or both fail

High cardinality, even distribution — avoid hot partitions.

GSI vs LSI GSI vs LSI

GSI مرن (أيّ وقت، capacity مستقلّ). LSI عند الإنشاء فقط (٥ أقصى).

GSI flexible (anytime, own capacity). LSI at creation only (max 5).

Transactions & TTL Transactions & TTL

Transactions give ACID (2× capacity). TTL auto-deletes at no WCU cost.

للحفظ السريع: Mnemonic:

للتفريق بين Query و Scan: Query = Precise (مفتاح مُحدَّد)، Scan = Sweep (يقرأ كل شيء). إذا رأيت كلمة "Scan" في حلّ مقترح — غالباً هو الإجابة الخاطئة في الامتحان.

Query vs Scan: Query = Precise (keyed), Scan = Sweep (reads all). If you see "Scan" as a proposed solution — it's usually the wrong exam answer.
